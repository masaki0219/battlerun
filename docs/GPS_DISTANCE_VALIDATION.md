# GPS距離フィルタの検証手順

## 目的と前提

ZELIOのGPS距離を他社アプリの値へ強制的に合わせるのではなく、水平精度不良、単発ジャンプ、GPS空白、微小ジッターによる系統的な水増しを減らす。Nike Run Clubなどの参考アプリは真値とせず、公称距離と実走ログを主な検証材料にする。

以下の数値は製品上の暫定目標であり、OSやGPSハードウェアが保証する数値ではない。

## 現在の処理経路

1. 記録画面を開いた時点から `BestForNavigation` / `distanceInterval: 0` でウォームアップする。Androidだけ `timeInterval: 1000` を指定する。
2. Androidは正確な位置情報 (`fine`)、iOSは取得できた点の実 `accuracy` を開始前に確認する。
3. 記録中はバックグラウンタスク、利用不可時はフォアグラウン監視のいずれか一方が `recordStore.appendRoutePoint` へ受信点を渡す。
4. 受信点は `functions/src/gpsProcessing.ts` の純粋関数を通る。アプリ側の `utils/gpsProcessing.ts` はその同一実装をre-exportする。
5. クライアントは正式採用済みのcommit点だけをFunctionsへ送る。Functionsは同じ純粋関数で、明示済みの `seg` を境界として再生し、その距離を活動、完了画面、個人記録、チャレンジ貢献の正式値にする。疎なcommit点のtimestampからFunctionsが空白を再推定すると、クライアント側だけが受け取ったMICRO_JITTERを「受信なし」と誤判定するため、採用済みルートの再生では新たな空白推定を行わない。

全生点はサーバーへ追加送信しない。Firestoreの既存上限は50,000点、1チャンク500点のままである。正式ルートはcommit点だけになるため、通常は従来より小さくなる。`gpsQuality` は座標を含まない小さな活動単位の集計だけを追加する。

## 開発用JSONの取得とリプレイ

正確な座標を含むため、受信点ログは既定で無効、サーバー送信なしである。検証用ビルドでだけ次を設定する。

```dotenv
EXPO_PUBLIC_GPS_DEBUG_EXPORT=1
```

1活動の終了時に、端末内AsyncStorageの `@zelio_latest_gps_debug_export_v1` へ最新の1件を保存し、Metroログの `[GPS_DEBUG_EXPORT]` に同じJSONを出力する。これを `gps-log.json` として安全な開発用場所へ保存し、次で再生する。座標を含むため、チケットや公開リポジトリへは添付しない。

```bash
npm run gps:replay -- gps-log.json > replay-result.json
```

しきい値の比較には、次の4項目を持つJSONを2つ目の引数に渡す。コードの既定値は不完全な設定で上書きしない。

```json
{
  "distanceMaxAccuracyM": 35,
  "maxRunningSpeedMps": 7,
  "gapSegmentMs": 15000,
  "minCommitDistanceM": 3
}
```

```bash
npm run gps:replay -- gps-log.json gps-config.json > replay-tuned.json
```

出力にはraw/正式距離と差、採否数、理由別件数、セグメント数、accuracyの中央値/P95、1kmごとの距離、処理後ルート、各点の判定結果が含まれる。アプリ本体と別の距離ロジックは持たない。アプリ内のaccuracy中央値/P95は長時間記録のメモリ使用を抑えるため、最大2,048点の決定的サンプルからの概算になる。

## 実走・静止試験

比較する各試験では、端末、持ち方、開始位置、時間帯をできるだけ揃える。毎回JSONを保存し、平均誤差だけでなく再現性と除外理由を見る。

### A. 開けた既知距離コース

- 400mトラックを5周し、合計2kmを3回以上記録する。
- ZELIOと参考用アプリを同時記録する。
- 正式な基準はトラック距離とし、開けた場所での平均誤差3%以内を暫定目標にする。

### B. 建物沿いコース

- 同じコースを3回記録する。
- 平均誤差5%以内を暫定目標とし、同一コースの結果が大きくばらつかないかを優先して見る。

### C. 静止試験

- 屋外で1回10分静止する。
- raw距離と正式距離、`MICRO_JITTER` 件数を確認し、正式距離の増加を極力小さくする。

### D. バックグラウン試験

- 画面をOFFにし、アプリをバックグラウンにして走る。
- バックグラウン点数、フォアグラウンフォールバック数、最大空白、復帰時のセグメントを確認する。
- 15秒以上の空白は前後が直線接続されていないことを必須とする。

### E. 一時停止試験

- 走行中に30秒停止する。
- 手動一時停止で停止・再開、オートポーズON、OFFをそれぞれ確認する。
- 停止中の点が距離に入らず、再開時に空白を接続せず、低速ウォーキングで不必要な自動停止が起きないことを見る。

## 調整時に残す記録

- 端术とOSバージョン、天候、コース種別、フォア/バックグラウン比率。
- 基準距離、raw距離、正式距離、誤差率。
- accuracy中央値/P95、精度除外、速度除外、微小ジッター、セグメント分割の各件数。
- 後から同じログを同じ設定で完全再生できるよう、使用した設定JSONを対にして保存する。

チューニングは特定の参考アプリへ合わせる係数ではなく、複数回の既知距離と再現性に基づいて行う。
