## 3. Phase 1 — 最大公約数の穴埋め（優先度: 高。ただし T-01 は例外的に低優先度）

### T-01 オートポーズ（工数: M。**実験的機能・優先度は低。Sprint 5 まで後回し**）
- **位置づけ**: GPS 単独でのオートポーズは、位置ジャンプやゆっくりランナーの誤停止・誤再開が起きやすい（Strava もモーションセンサーとの併用でこれに対処している）。初期リリースでは**デフォルト OFF**、設定内に「実験的機能」ラベルを付けて提供する。デフォルト値・優先度ともに初版から変更。
- **判定仕様（暫定・実測ログでの調整が前提）**:
  - GPS の水平精度（`expo-location` の accuracy 相当）が悪い（目安 30m 超）測位点は判定に使わない。
  - 直近1点の瞬間速度ではなく、直近 10〜15 秒の**速度の中央値**で判定する（外れ値に強くするため）。
  - 速度に加え、同じ時間窓での**移動距離（始点-終点の直線距離）**も条件に含め、両方が閾値を下回った場合のみ停止候補とする（信号待ちでの微小な GPS ドリフトによる誤発火を抑える）。
  - ラン/ウォークで閾値を分ける（初期値はあくまで暫定例であり、コード上も「暫定値・要チューニング」と明記すること。固定の絶対値として仕様化しない）。
  - 再開判定は停止判定より明確に高い閾値を要求するヒステリシスを設ける。
- **検証方法**: 判定ロジックを純関数として切り出し、実装時に実走ログ（GPS 点列 + 実際の一時停止/再開タイミング）を最低数件記録し、閾値の妥当性を検証してからデフォルト値を確定する。検証なしにこのタスクの「完了」を報告しない。
- **代替案**: リアルタイム自動停止をやめ、アップロード後にサーバー側で停止区間を推定する方式（オートポーズ非搭載時に Strava が採る方式に近い）も選択肢としてあり得る。この場合 HUD 側の変更が不要になる利点がある。Codex は着手前にどちらの方式を取るかユーザーに確認してよい。
- **設計上の注意**: 既存の手動一時停止は `(tabs)/_layout.tsx` で **GPS 追跡自体を止める**設計。オートポーズ中は自動再開の判定のために**位置追跡を止めてはならない**。`recordStore` に `pauseKind: 'manual' | 'auto' | null` を追加し、auto 中は追跡継続・距離/時間だけ除外する。再開時は既存の `seg: true` セグメント境界の仕組みをそのまま使う（サーバー側 `submitActivity` は変更不要のはず。要確認）。
- **対象**: `stores/recordStore.ts`, `app/(tabs)/_layout.tsx`, `app/(tabs)/record.tsx`（HUD に「自動停止中」表示）
- **受け入れ基準**: デフォルト OFF であること。静止時に HUD が自動停止表示になり時間・距離が増えない。歩き出すと自動再開し、停止中の移動距離が距離に含まれない。手動一時停止と競合しない（手動停止が常に優先）。閾値が実測ログなしの「確定仕様」として扱われていないこと。バックグラウンド中も動作（EAS build で確認、未確認なら明記）。

### T-02 音声コーチの設定拡充（工数: S）
- **仕様**: 音声ガイドを ON/OFF から設定制へ。読み上げトリガー: 距離ごと（0.5/1/2km）または時間ごと（5/10分）。読み上げ内容のトグル: 経過時間 / 距離 / 直近ラップペース / 平均ペース。開始前画面のボトムシートで設定、AsyncStorage 永続化。既定値は「1kmごと・距離+平均ペース」（NRC/adidas の既定に近い）。
- **対象**: `app/(tabs)/record.tsx`（読み上げロジックと設定 UI）、必要なら `stores/recordStore.ts`
- **受け入れ基準**: 設定どおりの間隔・内容で `expo-speech` が日本語読み上げする。ペースは `分'秒"` 形式（例「キロ 6分12秒」）。一時停止中は読み上げない。既存の目標達成・スタート読み上げは維持。

### T-03 自己ベスト（PR）とサマリーでの祝福（工数: M〜L。初版より工数増）
- **データモデル（二層に分離）**:
  - `users/{uid}.currentPersonalRecords`: 現存する有効な活動から算出した「現在の」PR。各項目に**元になった activityId** を持たせる: `{ fastest1k: { sec, activityId } | null, fastest5k: {...}, fastest10k: {...}, longestRunKm: {...}, maxElevationGainM: {...}, bestMonthKm: {...} }`
  - `users/{uid}/historicalAchievements/{id}`: 過去に PR を更新した事実の履歴（表彰目的。削除で遡って消さない）
- **最速区間の算出**: `pausedMs` 控除後の実走時間だけでは、どの 1km 区間の途中で一時停止が挟まったか分からず不正確。以下の情報を使ってスライディングウィンドウ（可変開始点で距離がちょうど Nkm になる区間の最短時間を探索）を実装する:
  - 各 GPS 点の timestamp（route point に保持されている想定。要確認）
  - `seg` セグメント境界、一時停止の開始・再開時刻
  - セグメントを跨ぐウィンドウは候補から除外（距離・時間とも不算入という既存方針と整合）
  - km 境界での時刻の線形補間
  - これは既存 `kmSplits()`（固定 km 境界でのラップ表示用）とは異なるアルゴリズムになる可能性が高い。流用できるかは実装時に判断する。
- **削除時の再計算**: `deleteActivity` 実行時、削除対象の活動が**いずれかの PR 項目の元 activityId と一致する場合のみ**、その項目を残りの有効な活動から再計算する（一致しなければ何もしないため、通常削除への追加コストはほぼゼロ）。次点がなければその項目を `null` に戻す。`historicalAchievements` は削除の影響を受けない。
- **クライアント**: サマリー画面（`app/record/summary.tsx`）で `newRecords` があれば「自己ベスト更新! 🎉」カードを表示。記録タブに「自己ベスト」セクション（1k/5k/10k/最長/最高月間）。
- **対象**: `functions/src/aggregateActivity.ts`（or `submitActivity.ts`）, `functions/src/deleteActivity.ts`, `types/`, `app/record/summary.tsx`, `app/(tabs)/stats.tsx`
- **受け入れ基準**: `cd functions && npm run build` 成功。最速区間算出の純関数に node での実測テストを追加（境界: 距離不足・seg 跨ぎ・pause 跨ぎ・km 境界補間）。削除時の再計算について「PR 元を削除した場合」「PR 元でない活動を削除した場合」両方を実測テストに含める。既存活動しかないユーザーでも壊れない（`currentPersonalRecords` 欠落時のフォールバック）。

### T-04 月間・年間統計（工数: M〜L。バックフィルを含むため初版より工数増）
- **仕様**: サーバーで `users/{uid}/monthlyStats/{YYYY-MM}` に `{ km, count, durationSec, elevationM }` を increment（`aggregateActivity` で加算、`deleteActivity` で減算。冪等化は既存の仕組みに合わせる）。記録タブに「月間」ビューを追加: 直近12ヶ月のバーチャート（`WeeklyBarChart` を汎用化 or 新規 `MonthlyBarChart`）、年間累計、月選択で当月の内訳。
- **バックフィル（初版からの追加）**: 現時点で `activities` の件数がまだ少ない（HANDOFF 記載時点で20件弱）ため、今のうちに過去分を埋めておく。1回限りの admin 用 Callable Function（または `scripts/` 配下の Node スクリプト）で、ユーザーごとに既存 `activities` をページングしながら月別集計し `monthlyStats` へ書き込む。二重実行防止のため `users/{uid}.monthlyStatsBackfilledAt` を記録する。件数が増えた後の再実行は分割・レート制限を検討する。
- **対象**: `functions/src/aggregateActivity.ts`, `functions/src/deleteActivity.ts`, 新規 `functions/src/backfillMonthlyStats.ts`（または Node スクリプト）, `firestore.rules`（本人のみ read。**ルール変更するので `npm run test:rules` にテスト追加必須**）, `app/(tabs)/stats.tsx`
- **受け入れ基準**: ルールテスト全件成功（本人 read 可 / 他人 read 拒否 / クライアント write 拒否）。バックフィル後、対象ユーザーの月別合計が既存 `activities` の実データと一致することを node で検証する。

### T-05 継続目標（週間目標）と進捗リング（工数: S）
- **仕様**: `users/{uid}.weeklyGoal: { type: 'distance' | 'days', value: number } | null` を本人が設定（記録タブから）。既存 `ProgressRing` で今週の進捗を記録タブ + ホームの週間カードに表示。達成時はローカル通知ではなく**画面内の祝福表示のみ**（通知で急かさない。9章参照)。「週3日」など日数型は休息日を前提とした健全な既定値（距離: 10km / 日数: 3日）を提案表示する。
- **対象**: `app/(tabs)/stats.tsx`, `app/(tabs)/battle.tsx`（週間カード）, `stores/authStore.ts`, `firestore.rules`（users 本人 update の許可フィールドに追加。ルールテスト追加）
- **受け入れ基準**: 設定・変更・解除ができ、リングが週の記録に追従（既存のリアルタイム購読を利用）。ルールテスト成功。

### T-06 ルート表示の強化: ペース色分け + km マーカー（工数: S〜M）
- **仕様**: 活動詳細（`app/activity/[id].tsx`）の地図で、ポリラインをラップペースに応じ3段階の色（速い=primary / 普通=中間 / 遅い=accent 系。**必ず `design_tokens.ts` に段階色トークンを追加して参照**）でセグメント分割描画。km 境界に小さな数字マーカー。
- **実装上の注意**: 既存 `kmSplits()` は区間ごとのラップタイム表示用の値を返すのみで、km 境界の緯度経度は持たない。地図描画には別の純関数（例: `buildRouteSplits(routePoints)`）を新規実装する必要がある。出力イメージ: `{ segments: [{ startIdx, endIdx, paceSecPerKm }], kmMarkers: [{ km, lat, lng }] }`。km 境界をまたぐ2点間は距離ベースで座標を線形補間して求める。
- **対象**: `utils/displayStats.ts`（新規関数追加）または新規 `utils/routeSplits.ts`, `app/activity/[id].tsx`, `design_tokens.ts`
- **受け入れ基準**: 新規純関数に node での実測テスト（km 境界の座標補間、seg 跨ぎ区間の分断）を追加する。seg 跨ぎ（一時停止）区間は線を引かない。ルートなし（歩数モード）活動では従来どおり地図非表示。

## 4. Phase 2 — 独自コンセプト「チーム戦 × 健全な自発性での行動開始」（優先度: 最高＝差別化の核）

> 思想: 「走らされる」のではなく「自分で決めて走り出す」を、チームが**罰や圧力なしで**後押しする。数値報酬・ランキング圧より、「宣言 → 仲間の応援 → 実行 → 祝福」の正のループを設計する。Phase 1 と並行実装可。ユーザーの意向次第ではこちらを先行してよい。

### T-10 出撃宣言（インテント宣言）（工数: L）
- **コンセプト**: 参加中のチャレンジに対し「今日の19時ごろ走る」と宣言する。宣言は自分との約束であり、チームには「応援できる対象」として見える。
- **データモデル**: `battles/{battleId}/declarations/{uid}_{localDate}`（1日1件/人）:
  `{ uid, localDate: string（例 "2026-07-20"。クライアントが本人のローカル日付として明示送信する。サーバーの UTC 変換のみに依存すると日付境界・海外滞在時に誤判定するため）, timeZone: string（例 "Asia/Tokyo"）, plannedAt: Timestamp, note?: string(20字以内・禁止語チェックは lib/validation/bannedWords.ts を再利用), status: 'planned' | 'done' | 'expired', createdAt }`
- **フロー**:
  1. ホーム（チャレンジ参加中のみ）に「今日の出撃宣言」カード。時間帯チップ（朝/昼/夕方/夜 or 時刻ピッカー。`PeriodPicker` の実装パターン参考）で宣言。
  2. 宣言時刻にローカル通知「宣言した時間になりました。準備ができたらスタート!」→ タップでランタブへディープリンク（既存 scheme `zelio`）。**リマインドは1回だけ。スヌーズや再督促はしない。**
  3. **宣言の `done` 更新は必ずサーバー側（Functions）で行う。クライアントに直接更新させない**（初版からの変更点。クライアント改ざん・通信途中失敗・異常記録での誤達成を防ぐため）。`submitActivity` の成功処理内（または直後のトリガー）で、活動の uid と startedAt から該当ユーザーの localDate を算出し、参加中の各バトルについて `battles/{battleId}/declarations/{uid}_{localDate}` が `status: 'planned'` であれば `done` に更新する。改ざん耐性を優先する場合、localDate はクライアント申告値をそのまま信頼せず、活動の `startedAt` + ユーザーの `timeZone` 設定からサーバー側で独自に算出することも検討する。
  4. 当日中に実行されなかった宣言は表示上そっと消える（`expired` はクライアント表示ロジックで判定可。**バッチ処理・未達通知・未達の対外表示は作らない**）。
- **チーム表示**: ホームのチーム内ランキングカード付近に「今日の宣言」リスト（名前 + 時間帯 + 応援ボタン🔥）。応援は `declarations/{id}/cheers/{fromUid}` に1人1件、Functions（新規 `onCheerCreated`）が宣言者へプッシュ「◯◯さんが応援しています」。
- **ルール**: 宣言の create は本人のみ・参加中バトルのみ。**`status` フィールドへのクライアントからの書き込みは拒否し、`done` への更新は Functions（Admin SDK）のみが行えるようにする。** read はバトル参加者。cheers は参加者が自分の uid でのみ create。**ルールテスト必須**（本人以外の宣言作成拒否 / 非参加者の read 拒否 / cheer なりすまし拒否 / クライアントから `status: 'done'` への直接書き込み拒否）。
- **対象**: `app/(tabs)/battle.tsx`, 新規 `components/battle/DeclarationCard.tsx`, `stores/battleStore.ts`, `lib/notifications.ts`（ローカル通知）, `functions/src/submitActivity.ts`（または新規トリガー。宣言の達成確定）, `functions/src/`（cheer 通知）, `firestore.rules`, `tests/firestore-rules.test.ts`
- **受け入れ基準**: 宣言→通知→ワンタップでランタブ→記録完了→**サーバー側で** `done` に更新、の一連が動く。未達時に本人・他人ともネガティブ表示が一切出ない。禁止語が note で弾かれる。クライアントから `status` への直接書き込みがルールで拒否されることを含め、ルールテスト成功。

### T-11 「いま走ってる仲間」ライブプレゼンス + 走行中応援（工数: L）
- **コンセプト**: 仲間が走り出した気配が最大の着火剤。「いま2人が走っています」が見えるだけで自発的スタートが生まれる。
- **データモデル（セッション単位。初版からの変更点）**: 固定ドキュメント `presence/{uid}` は、ラン開始のたびに再利用されるため前回ランの応援が残ってしまう。代わりにセッション単位で管理する:
  - `battles/{battleId}/runSessions/{sessionId}`: `{ uid, startedAt, lastBeatAt, visible: boolean }`（`sessionId` はクライアント生成の UUID）
  - `battles/{battleId}/runSessions/{sessionId}/cheers/{fromUid}`（1セッション1人1件）
  - 記録終了時にセッションドキュメントを削除する（または `endedAt` を立てて非表示化する）。
- **書き込み頻度**: `lastBeatAt` の更新は 60 秒ではなく **120 秒**間隔に緩和し、購読も「ホーム画面表示中」かつ「参加バトル1件」に限定する（1時間走ると1人あたり相応の書き込みが発生するため、頻度と購読範囲の両方を絞る）。
- **実装方式の選定（着手前にユーザーと確認）**: 本機能はプレゼンス（オンライン/オフライン状態）用途であり、接続断検知の `onDisconnect` を持つ **Firebase Realtime Database** の方が本来適している。一方、本プロジェクトは全面的に Firestore を使っており RTDB 新規導入はコストを伴う。**このタスクは Firestore 版（上記のセッションドキュメント方式）と RTDB 版のどちらで実装するかを、着手前に必ずユーザーへ確認してから進めること。**
- **プライバシー**: プロフィールに「走行中の表示を仲間に公開」トグル（**既定 OFF = opt-in**）。位置情報は一切共有しない（「走っている」という事実のみ）。
- **応援**: 走行中メンバーの行に応援ボタン → 該当セッションの `cheers/{fromUid}` へ書き込み → Functions がプッシュ。**ランナー側**: 記録 HUD が応援を購読し、受信時にハプティクス + 音声ガイド ON なら「◯◯さんから応援が届きました」を読み上げ。
- **対象**: `stores/recordStore.ts` or 新規 `hooks/usePresence.ts`, `app/(tabs)/battle.tsx`, `app/(tabs)/record.tsx`, `functions/src/`, `firestore.rules`（または RTDB ルール） + ルールテスト
- **受け入れ基準**: opt-in しない限り自分が表示されない。記録終了後にセッションが速やかに消える。**同じユーザーが2回連続で走った場合、1回目の応援が2回目のセッションに残らない**（セッション分離の確認）。応援がランタイム中の HUD に届く。読み書き回数が過大でない（購読範囲の限定を確認）。

### T-12 プロセス貢献の可視化（工数: M）
- **コンセプト**: 距離ランキング（結果）だけだと速い人しか輝けない。「宣言達成数」「今週の参加日数」という**過程の貢献**をチーム内で称える。順位・集計への影響は与えない（チーム戦の勝敗は従来どおり距離）。
- **仕様**: participant ドキュメントに `declarationsDone: number`, `activeDaysThisWeek: number` を集計（`aggregateActivity` 拡張 or クライアント表示時に declarations から算出。書き込み競合が少ない後者を推奨）。`TeamRankingCard` に小さな🔥バッジ（今週の宣言達成数）を表示。「今週チームで一番早起きランをした人」などの表彰はバトル結果画面に1行追加（`finishBattle` 拡張、任意）。
- **受け入れ基準**: 距離ランキングの並びと集計値に一切影響しない。0 件のユーザーにネガティブ表示（「0回」の赤字等）をしない。

### T-13 健全性ガードレール（工数: S）
- **仕様**:
  1. **活動量の変化に気づく情報カード（「過負荷警告」ではない）**: 固定の絶対閾値（例: 先週比+50%かつ15km超）は、初心者（0km→16km）と上級者（50km→76km）を同列に扱ってしまうため避ける。判定はユーザー自身の**過去4週間の中央値**と活動日数を基準にする。過去4週間に十分な記録（目安3件以上）がない新規ユーザーには表示しない。関数名も判定を断定しない名前にする（例: `isOverload()` ではなく `unusualIncreaseNotice()`）。表示文言は「今週はいつもより活動量が増えています。疲れがある場合は休息も選択肢です。」のように、警告調ではなく情報提供として1回だけ表示する（通知はしない）。
  2. **静音時間**: すべてのローカル通知（宣言リマインド含む）は 22:00〜7:00 に発火させない（時間帯宣言が深夜ならリマインドを出さない）。
  3. **文言ガイドの適用**: 9章の禁止表現をアプリ内文言・通知文から grep で確認する。
- **対象**: `utils/displayStats.ts`（中央値ベースの判定関数を新規追加。既存 `weekOverWeek()` は先週比のみで中央値を持たないため、そのまま流用せず新規実装するか拡張する）, `app/(tabs)/stats.tsx`
- **受け入れ基準**: 新規ユーザー（過去4週間の記録が不足）にカードが表示されないこと。中央値ベースの判定を node で実測テストする。カードが同一週に再表示されない（AsyncStorage で既読管理）。22時以降の宣言でリマインド通知がスケジュールされないことをコードで保証。

### T-21 詳細: HealthKit / Health Connect 連携（読み込み優先。初版の「書き出しのみ」から方針転換）
- 目的の再定義: 「Zelio 記録を Health アプリへ書き出す」ことより、「Apple Watch や他アプリで既に記録した人が、Zelio でもう一度 GPS 記録し直さずに済む」ことの価値が大きい。優先順位を反転する。
  1. HealthKit（iOS）からランニングワークアウト + ルートを読み込む。
  2. Health Connect（Android）から同様に読み込む。
  3. ワークアウトの source（記録元アプリ/デバイス）で重複排除する。Zelio 自身が過去に書き出した記録を再度読み込む無限ループを避けるため、Zelio 書き出し分には識別可能な source 名を付け、読み込み時に除外する。
  4. 読み込んだ記録をチャレンジの得点対象にするかはサーバー側（`submitActivity` 相当）で判定する。手動入力か・ルートの有無・source が何かを保存する。**外部アプリ由来の記録をチーム戦の得点対象に無制限に含めるかどうかは不正対策上の論点であり、実装前に得点ポリシーをユーザーと合意すること（着手のブロッカー）。**
  5. 読み込みが安定した後、Zelio 記録を Health へ書き出す opt-in 機能を追加する（初版で想定していた機能）。
- 対象: 新規のヘルス連携モジュール、`functions/src/`（得点対象判定ロジック）
- 受け入れ基準: 重複記録が読み込まれないこと、Zelio 書き出し分の再読み込みループが起きないことをテストする。

### T-28 詳細: Google / Apple サインイン（Apple 必須表現を修正）
- 現状はメール/パスワード認証のみのため、Apple ガイドライン 4.8（第三者ログインを導入する場合、同等のプライバシー条件を満たすログイン手段も提供する）は**現時点では適用対象外**。「ストア審査上 Apple はほぼ必須」という初版の表現は不正確だったため削除する。
- 実際の制約: **Google ログインを追加する場合**、Apple の審査では Apple ログイン等の同等の手段も同時に用意することが求められる可能性が高い。したがって計画は以下のいずれかとする。
  - Google のみ追加 → 審査リスクあり（Apple 4.8 対応の要否を事前に確認）
  - Google + Apple を同時追加 → 審査リスク低減
- 対象: 元のまま（`expo-apple-authentication` / `expo-auth-session` は導入済み、配線のみ）
- 受け入れ基準: Google ログインを追加するリリースでは、Apple ログインの同時実装可否をユーザーと確認してから着手する。

## 6. 実装順序の推奨（改訂: 独自コンセプトを最優先に）

本レポート自身が「差別化の核＝独自コンセプト（第4章）」と位置づけているため、記録体験の穴埋め（Phase 1）を全て先に終わらせてから着手する初版の順序は、報告書の優先度づけと矛盾していた。以下へ改める。

```
Sprint 1: T-02, T-10, T-13        ← 音声設定 + 独自コアの最小形(サーバー確定版の出撃宣言) + 健全性ガードレール
Sprint 2: T-03, T-04, T-06        ← PR(二層モデル+削除時再計算) + 月間統計(バックフィル込み) + ルート表示強化
Sprint 3: T-21                    ← HealthKit/Health Connect 読み込み優先(得点ポリシーの合意が前提)
Sprint 4: T-11, T-12              ← ライブプレゼンス(セッション単位) + 過程貢献
Sprint 5: T-01, T-05 + Phase 3 から選択 ← オートポーズ(実走ログでの閾値検証後)、週間目標、磨き込み
```

- T-01（オートポーズ）は実験的機能・低優先度のため最終スプリントへ後回しにした。実走ログでの閾値検証が終わるまで本実装のデフォルト値を確定しない。
- Functions / ルール変更を伴うタスク（T-03, T-04, T-05, T-10, T-11）は、**デプロイ待ち行列が混ざらないよう** HANDOFF の「未解決・要確認」に未デプロイ関数を必ず列挙すること。
- 1タスク = 1まとまりで実装し、複数タスクを1つの巨大変更にしない。

## 9. 健全性ガイドライン（全タスク共通の文言・挙動規約）

本アプリの差別化思想は「**健全な自発性**」。以下を全機能・全文言に適用する。

**禁止**
- 未達成・未実行をネガティブに表示すること（「サボり」「未達」「◯日走っていません」等）
- 他人との比較で焦らせる通知（「◯◯さんはもう走りました」）
- 連続記録が切れることへの脅し文言、損失回避を煽る表現（「ストリークが失われます!」）
- 1日に複数回のリマインド、深夜帯（22:00〜7:00）の通知
- 宣言・プレゼンスのデフォルト公開（すべて opt-in）

**推奨**
- 行動開始のハードルを下げる（ワンタップ導線、宣言からの直行）
- 実行した事実だけを祝福する（「宣言達成!」「今週3日目!」）
- 応援は「送る側の自発的行為」として設計し、送信を促す通知は出さない
- 休息を正当化する文言（「休息も練習のうち」）
