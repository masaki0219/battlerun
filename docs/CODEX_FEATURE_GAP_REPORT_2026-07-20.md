# ZELIO 機能ギャップレビュー & Codex 実装指示書

作成日: 2026-07-20
対象リポジトリ: `Desktop/ZELIO/Zelio`（ブランチ: `feat/ui-consolidation`）
目的: 人気ランニングアプリ（Strava / Nike Run Club / adidas Running / ASICS Runkeeper / Garmin Connect）の「最大公約数」となる機能・デザインを満たしつつ、便利機能を追加し、さらに本アプリ独自のコンセプト **「チーム戦 × 健全な自発性での行動開始」** を実装する。

## 0. Codex への必読事項（作業前に必ず守ること）

1. 最初に `CLAUDE.md` → `AGENTS.md` → `HANDOFF.md` を読むこと。本書と矛盾する場合は最新の `HANDOFF.md` と実コードを優先する。
2. **ユーザーの許可なしに commit / push / reset / rebase をしない。**
3. 色は必ず `design_tokens.ts` から参照する。コンポーネントに hex リテラルを書かない（コメント中も禁止）。
4. 検証コマンド（実行していない確認を「成功」と報告しない）:
   - `npx tsc --noEmit`（型チェック）
   - `npx expo export --platform ios`（バンドル確認）
   - `cd functions && npm run build`（Functions 変更時）
   - `npm run test:rules`（**firestore.rules を変更した場合は必須**。Firebase エミュレータ + Java が必要）
   - `npm run test:unit`（純関数のユニットテスト）
5. 各タスク完了時に `HANDOFF.md` を更新し、「次にやること」を具体的な1件にする。
6. 前提: `submitActivity`（localId 冪等化 / pausedMs / seg / alt）と `deleteActivity` は**実装済みだが Functions 未デプロイ**。デプロイはユーザー作業。Functions に依存する動作確認はデプロイ後であることを明記して報告する。
7. Expo Go の制約: バックグラウンド GPS・ウィジェット・HealthKit はEAS development build が必要。Expo Go で確認できない項目は「未確認」と報告する。
8. 通知文言・チーム機能の文言は「9. 健全性ガイドライン」に従う（煽り・罰・比較で焦らせる表現を禁止）。

## 2. 人気アプリ「最大公約数」との比較（ギャップ分析）

◎=十分 / △=部分的 / ✗=なし。「GCD」= Strava / NRC / adidas Running / Runkeeper / Garmin のほぼ全てが持つ機能。

| 機能 | GCD | ZELIO | ギャップ |
|---|---|---|---|
| GPS 記録・地図・ラップ | ● | ◎ | なし |
| **オートポーズ** | ● | ✗ | 手動一時停止のみ。信号待ちで自動停止しない |
| **音声コーチの設定**（間隔・ペース読み上げ） | ● | △ | ON/OFF のみ。距離1km固定、ペース/時間の読み上げなし |
| **自己ベスト（PR）**（最速1k/5k/10k 等） | ● | △ | 最長距離のみ。速度系 PR とサマリーでの祝福なし |
| **月間・年間統計** | ● | △ | 週間のみ。履歴も直近50件で頭打ち |
| **継続目標**（週間距離/回数目標） | ● | ✗ | 単発ラン目標のみ |
| ヘルスケア連携（HealthKit / Health Connect） | ● | ✗ | なし |
| ルートのペース色分け・km マーカー | ● | ✗ | 単色ポリラインのみ |
| シューズ（ギア）管理 | ○(多数) | ✗ | なし |
| インターバル/ワークアウト | ○(多数) | ✗ | なし |
| トレーニングプラン | ○(多数) | ✗ | なし |
| GPX エクスポート | ○(多数) | ✗ | なし |
| 天気表示 | ○(多数) | ✗ | なし |
| ウィジェット / Live Activities | ○(多数) | ✗ | なし |
| ダークモード切替 | ● | △ | `DarkColors` トークンは存在するがアプリ全体の切替なし |
| ソーシャル（応援/リアクション） | ● | △ | 事後リアクションのみ。**走行中の応援なし** |

## 3. Phase 1 — 最大公約数の穴埋め（優先度: 高）

### T-01 オートポーズ（工数: M）
- **仕様**: GPS モード記録中、速度が閾値未満（目安 0.55 m/s）の状態が 5 秒続いたら自動一時停止。閾値超（目安 1.2 m/s、ヒステリシス必須）の点を検知したら自動再開。開始前画面に「オートポーズ」トグル（デフォルト ON、AsyncStorage 永続化）。歩数モードでは非表示・無効。
- **設計上の注意**: 既存の手動一時停止は `(tabs)/_layout.tsx` で **GPS 追跡自体を止める**設計。オートポーズ中は自動再開の判定のために**位置追跡を止めてはならない**。`recordStore` に `pauseKind: 'manual' | 'auto' | null` を追加し、auto 中は追跡継続・距離/時間だけ除外する。再開時は既存の `seg: true` セグメント境界の仕組みをそのまま使う（サーバー側 `submitActivity` は変更不要のはず。要確認）。
- **対象**: `stores/recordStore.ts`, `app/(tabs)/_layout.tsx`, `app/(tabs)/record.tsx`（HUD に「自動停止中」表示）
- **受け入れ基準**: 静止5秒で HUD が自動停止表示になり時間・距離が増えない。歩き出すと自動再開し、停止中の移動距離が距離に含まれない。手動一時停止と競合しない（手動停止が常に優先）。バックグラウンド中も動作（EAS build で確認、未確認なら明記）。

### T-02 音声コーチの設定拡充（工数: S）
- **仕様**: 音声ガイドを ON/OFF から設定制へ。読み上げトリガー: 距離ごと（0.5/1/2km）または時間ごと（5/10分）。読み上げ内容のトグル: 経過時間 / 距離 / 直近ラップペース / 平均ペース。開始前画面のボトムシートで設定、AsyncStorage 永続化。既定値は「1kmごと・距離+平均ペース」（NRC/adidas の既定に近い）。
- **対象**: `app/(tabs)/record.tsx`（読み上げロジックと設定 UI）、必要なら `stores/recordStore.ts`
- **受け入れ基準**: 設定どおりの間隔・内容で `expo-speech` が日本語読み上げする。ペースは `分'秒"` 形式（例「キロ 6分12秒」）。一時停止中は読み上げない。既存の目標達成・スタート読み上げは維持。

### T-03 自己ベスト（PR）とサマリーでの祝福（工数: M）
- **仕様**: サーバー集計で `users/{uid}.personalRecords` を保持: `{ fastest1kSec, fastest5kSec, fastest10kSec, longestRunKm, maxElevationGainM, bestMonthKm }`。`aggregateActivity`（または `submitActivity` の集計部）でルートの累積距離配列からスライディングウィンドウ + 線形補間で最速 1k/5k/10k を算出（`seg` 跨ぎは除外、`pausedMs` 控除後の実走時間ベース）。更新があれば活動ドキュメントに `newRecords: string[]` を保存。
- **クライアント**: サマリー画面（`app/record/summary.tsx`）で `newRecords` があれば「自己ベスト更新! 🎉」カードを表示。記録タブに「自己ベスト」セクション（1k/5k/10k/最長/最高月間）。`deleteActivity` での PR 巻き戻しは**行わない**（バッジと同じ方針。HANDOFF の設計メモと整合）。
- **対象**: `functions/src/aggregateActivity.ts`（or `submitActivity.ts`）, `types/`, `app/record/summary.tsx`, `app/(tabs)/stats.tsx`
- **受け入れ基準**: `cd functions && npm run build` 成功。最速区間算出の純関数に node での実測テストを追加（境界: 距離不足・seg 跨ぎ・補間）。既存活動しかないユーザーでも壊れない（`personalRecords` 欠落時のフォールバック）。

### T-04 月間・年間統計（工数: M）
- **仕様**: サーバーで `users/{uid}/monthlyStats/{YYYY-MM}` に `{ km, count, durationSec, elevationM }` を increment（`aggregateActivity` で加算、`deleteActivity` で減算。冪等化は既存の仕組みに合わせる）。記録タブに「月間」ビューを追加: 直近12ヶ月のバーチャート（`WeeklyBarChart` を汎用化 or 新規 `MonthlyBarChart`）、年間累計、月選択で当月の内訳。履歴50件制限は据え置きでよい（集計はサーバー値を使うため）。
- **対象**: `functions/src/aggregateActivity.ts`, `functions/src/deleteActivity.ts`, `firestore.rules`（本人のみ read。**ルール変更するので `npm run test:rules` にテスト追加必須**）, `app/(tabs)/stats.tsx`
- **受け入れ基準**: ルールテスト全件成功（本人 read 可 / 他人 read 拒否 / クライアント write 拒否）。過去分のバックフィルはしない（今月以降から積み上がる旨を UI に注記）。

### T-05 継続目標（週間目標）と進捗リング（工数: S）
- **仕様**: `users/{uid}.weeklyGoal: { type: 'distance' | 'days', value: number } | null` を本人が設定（記録タブから）。既存 `ProgressRing` で今週の進捗を記録タブ + ホームの週間カードに表示。達成時はローカル通知ではなく**画面内の祝福表示のみ**（通知で急かさない。9章参照)。「週3日」など日数型は休息日を前提とした健全な既定値（距離: 10km / 日数: 3日）を提案表示する。
- **対象**: `app/(tabs)/stats.tsx`, `app/(tabs)/battle.tsx`（週間カード）, `stores/authStore.ts`, `firestore.rules`（users 本人 update の許可フィールドに追加。ルールテスト追加）
- **受け入れ基準**: 設定・変更・解除ができ、リングが週の記録に追従（既存のリアルタイム購読を利用）。ルールテスト成功。

### T-06 ルート表示の強化: ペース色分け + km マーカー（工数: S）
- **仕様**: 活動詳細（`app/activity/[id].tsx`）の地図で、ポリラインをラップペースに応じ3段階の色（速い=primary / 普通=中間 / 遅い=accent 系。**必ず `design_tokens.ts` に段階色トークンを追加して参照**）でセグメント分割描画。km 境界に小さな数字マーカー。`kmSplits()` の出力を再利用する。
- **受け入れ基準**: seg 跨ぎ（一時停止）区間は線を引かない。ルートなし（歩数モード）活動では従来どおり地図非表示。

## 4. Phase 2 — 独自コンセプト「チーム戦 × 健全な自発性での行動開始」（優先度: 最高＝差別化の核）

> 思想: 「走らされる」のではなく「自分で決めて走り出す」を、チームが**罰や圧力なしで**後押しする。数値報酬・ランキング圧より、「宣言 → 仲間の応援 → 実行 → 祝福」の正のループを設計する。Phase 1 と並行実装可。ユーザーの意向次第ではこちらを先行してよい。

### T-10 出撃宣言（インテント宣言）（工数: L）
- **コンセプト**: 参加中のチャレンジに対し「今日の19時ごろ走る」と宣言する。宣言は自分との約束であり、チームには「応援できる対象」として見える。
- **データモデル**: `battles/{battleId}/declarations/{uid_YYYYMMDD}`（1日1件/人）:
  `{ uid, plannedAt: Timestamp, note?: string(20字以内・禁止語チェックは lib/validation/bannedWords.ts を再利用), status: 'planned' | 'done' | 'expired', createdAt }`
- **フロー**:
  1. ホーム（チャレンジ参加中のみ）に「今日の出撃宣言」カード。時間帯チップ（朝/昼/夕方/夜 or 時刻ピッカー。`PeriodPicker` の実装パターン参考）で宣言。
  2. 宣言時刻にローカル通知「宣言した時間になりました。準備ができたらスタート!」→ タップでランタブへディープリンク（既存 scheme `zelio`）。**リマインドは1回だけ。スヌーズや再督促はしない。**
  3. `submitActivity` 成功時、クライアントが当日の自分の宣言を `done` に更新。サマリー画面に「宣言達成!」の祝福表示。
  4. 当日中に実行されなかった宣言は表示上そっと消える（`expired` はクライアント表示ロジックで判定可。**バッチ処理・未達通知・未達の対外表示は作らない**）。
- **チーム表示**: ホームのチーム内ランキングカード付近に「今日の宣言」リスト（名前 + 時間帯 + 応援ボタン🔥）。応援は `declarations/{id}/cheers/{fromUid}` に1人1件、Functions（新規 `onCheerCreated`）が宣言者へプッシュ「◯◯さんが応援しています」。
- **ルール**: 宣言の create/update は本人のみ・参加中バトルのみ。read はバトル参加者。cheers は参加者が自分の uid でのみ create。**ルールテスト必須**（本人以外の宣言作成拒否 / 非参加者の read 拒否 / cheer なりすまし拒否）。
- **対象**: `app/(tabs)/battle.tsx`, 新規 `components/battle/DeclarationCard.tsx`, `stores/battleStore.ts`, `lib/notifications.ts`（ローカル通知）, `functions/src/`（cheer 通知）, `firestore.rules`, `tests/firestore-rules.test.ts`
- **受け入れ基準**: 宣言→通知→ワンタップでランタブ→記録完了で `done` の一連が動く。未達時に本人・他人ともネガティブ表示が一切出ない。禁止語が note で弾かれる。ルールテスト成功。

### T-11 「いま走ってる仲間」ライブプレゼンス + 走行中応援（工数: L）
- **コンセプト**: 仲間が走り出した気配が最大の着火剤。「いま2人が走っています」が見えるだけで自発的スタートが生まれる。
- **データモデル**: `battles/{battleId}/presence/{uid}`: `{ startedAt, lastBeatAt, visible: boolean }`。記録中クライアントが 60 秒ごとに `lastBeatAt` を更新（フォアグラウンドのみで可。バックグラウンド書き込みはしない）。表示側は `lastBeatAt` が 3 分以内のものを「走行中」と判定（サーバー削除バッチ不要）。
- **プライバシー**: プロフィールに「走行中の表示を仲間に公開」トグル（**既定 OFF = opt-in**）。位置情報は一切共有しない（「走っている」という事実のみ）。
- **応援**: 走行中メンバーの行に応援ボタン → `presence/{uid}/cheers/{fromUid}`（1ラン1件）→ Functions がプッシュ。**ランナー側**: 記録 HUD が応援を購読し、受信時にハプティクス + 音声ガイド ON なら「◯◯さんから応援が届きました」を読み上げ（Strava のライブ応援に相当。GCD 超えの便利機能）。
- **対象**: `stores/recordStore.ts` or 新規 `hooks/usePresence.ts`, `app/(tabs)/battle.tsx`, `app/(tabs)/record.tsx`, `functions/src/`, `firestore.rules` + ルールテスト
- **受け入れ基準**: opt-in しない限り自分が表示されない。記録停止後 3 分以内に表示から消える。応援がランタイム中の HUD に届く。Firestore 読み書き回数が過大でない（presence 購読はホーム表示中のみ、参加バトル1件に限定）。

### T-12 プロセス貢献の可視化（工数: M）
- **コンセプト**: 距離ランキング（結果）だけだと速い人しか輝けない。「宣言達成数」「今週の参加日数」という**過程の貢献**をチーム内で称える。順位・集計への影響は与えない（チーム戦の勝敗は従来どおり距離）。
- **仕様**: participant ドキュメントに `declarationsDone: number`, `activeDaysThisWeek: number` を集計（`aggregateActivity` 拡張 or クライアント表示時に declarations から算出。書き込み競合が少ない後者を推奨）。`TeamRankingCard` に小さな🔥バッジ（今週の宣言達成数）を表示。「今週チームで一番早起きランをした人」などの表彰はバトル結果画面に1行追加（`finishBattle` 拡張、任意）。
- **受け入れ基準**: 距離ランキングの並びと集計値に一切影響しない。0 件のユーザーにネガティブ表示（「0回」の赤字等）をしない。

### T-13 健全性ガードレール（工数: S）
- **仕様**:
  1. **過負荷注意**: 今週距離が先週比 +50% 超かつ 15km 超のとき、記録タブに「今週はよく走っています。休息も練習のうち」という**情報カード**を1回だけ表示（通知はしない）。判定は既存 `weekOverWeek()` を再利用。
  2. **静音時間**: すべてのローカル通知（宣言リマインド含む）は 22:00〜7:00 に発火させない（時間帯宣言が深夜ならリマインドを出さない）。
  3. **文言ガイドの適用**: 9章の禁止表現をアプリ内文言・通知文から grep で確認する。
- **受け入れ基準**: 過負荷カードが同一週に再表示されない（AsyncStorage で既読管理）。22時以降の宣言でリマインド通知がスケジュールされないことをコードで保証。

## 5. Phase 3 — 便利機能の拡張（優先度: 中。Phase 1・2 完了後）

| ID | 機能 | 概要 | 工数 | 備考 |
|---|---|---|---|---|
| T-20 | インターバルワークアウト | 「ダッシュ1分+ジョグ2分×5」等のシンプルなビルダー + 区間切替の音声/バイブ誘導 | L | `recordStore` にワークアウト状態を追加 |
| T-21 | HealthKit / Health Connect 書き出し | 保存成功時にワークアウトを書き込み(opt-in) | L | **EAS dev build 必須**。`react-native-health` / `expo-health-connect` 系。Expo Go では動作しない旨を UI に明示 |
| T-22 | GPX エクスポート | 活動詳細から本人のみ。ルートチャンクを GPX 化し `expo-sharing` で共有 | S | route チャンクは本人 read 可の既存ルールで可 |

## 6. 実装順序の推奨

```
Sprint 1: T-01, T-02, T-05        ← 記録体験を GCD 水準へ(小さく速く)
Sprint 2: T-10, T-13              ← 独自コアの最小形(宣言 + ガードレール)
Sprint 3: T-03, T-04              ← サーバー集計系(PR・月間)。Functions デプロイをまとめる
Sprint 4: T-11, T-12              ← ライブプレゼンス + 応援 + 過程貢献
Sprint 5: T-06 + Phase 3 から選択 ← 磨き込み
```

- Functions / ルール変更を伴うタスク（T-03, T-04, T-05, T-10, T-11）は、**デプロイ待ち行列が混ざらないよう** HANDOFF の「未解決・要確認」に未デプロイ関数を必ず列挙すること。
- 1タスク = 1まとまりで実装し、複数タスクを1つの巨大変更にしない。

## 7. デザイン指針（最大公約数）

- 人気アプリ共通のデザイン文法に合わせる: **大きな数値のヒーロー表示（距離が最上位）**、スタートボタンは常に1タップ以内、記録中はダーク面 HUD（実装済み）、サマリーは「地図 → 主要数値 → ラップ → 共有」の順。
- 新規 UI はすべて `design_tokens.ts` のトークンと既存コンポーネント（`Card` / `Button` / `SectionHeader` / `ProgressRing` / `StreakChip` 等）を再利用する。新しい色が必要な場合はトークンを追加してから使う。
- 独自機能（宣言・応援）の色は accent（オレンジ）系 = 「熱・応援」、達成表示は primary（パイン）系 = 「落ち着いた祝福」で統一する。

## 9. 健全性ガイドライン（全タスク共通の文言・挙動規約）

本アプリの差別化思想は「**健全な自発性**」。以下を全機能・全文言に適用する。

**禁止**
- 未達成・未実行をネガティブに表示すること（「サボり」「未達」「◯日走っていません」等）
- 他人との比較で焦らせる通知（「◯◯さんはもう走りました」）
- 連続記録が切れることへの脅し文言、損失回避を煽る表現（「ストリークが失われます!」）
- 1日に複数回のリマインド、深夜帯（22:00〜7:00）の通知
- 宣言・プレゼンスのデフォルト公開（すべて opt-in）

**推奨**
- 行動開始のハードルを下げる（ワンタップ導線、宣言からの直行）
- 実行した事実だけを祝福する（「宣言達成!」「今週3日目!」）
- 応援は「送る側の自発的行為」として設計し、送信を促す通知は出さない
- 休息を正当化する文言（「休息も練習のうち」）
